# Job Hunt Agent

An LLM agent that reads a job description, scores you against it using evidence
retrieved from your own resume and project write-ups, and drafts tailored resume
bullets — refusing to draft any bullet it cannot ground in a document you
actually wrote.

It is decision support, not an auto-applier. It does not submit anything
anywhere. A human always presses send.

run, including the trace and a refusal, generated by

  │                                    ▼                                       │
  │   ┌────────────────────────────────────────────────────────────────────┐   │
  │   │ parse_requirements (Claude)     retrieve_evidence (BM25, no model) │   │
  │   │ score_match        (Claude)     draft_bullets     (Claude)         │   │
  │   └────────────────────────────────┬───────────────────────────────────┘   │
  │                                    │  after draft_bullets, always          │

  │                        guardrail.enforce()   ← grounding check, in code    │

`retrieve_evidence` reads a BM25 index built at startup from
`app/corpus/documents/*.md` — your resume and project write-ups, chunked at the
markdown section level so a citation points at a paragraph rather than a whole
document.

## How the agent loop works

**A planner decides every step.** `planner.next_action(goal, tool_schemas,
trace_so_far)` is one Claude call given the goal, the current run state, the
four tools as real tool definitions, and a compact rendering of everything that
has happened so far. It returns one tool call or `finish`. The order is not
hard-coded anywhere — if you script the planner to retrieve before parsing, the
loop does exactly that, and there is a test asserting it.

Each planner-facing tool schema carries a required `why` string. The dispatcher
strips it before calling the tool and puts it in the trace, which is where the
"why chosen" column on the result page comes from. The tools themselves have no
business taking a rationale argument.

**The loop is bounded.** It terminates on `finish` or at `MAX_STEPS`, whichever
comes first, and records which in `terminated_reason`.

**Error policy is per call**, and it is three distinct things that are easy to
conflate:

| Failure | Response |
|---|---|
| Call exceeds `TOOL_TIMEOUT_S` | Abandon it, classify as `upstream_timeout`, treat as transient |
| Transient upstream error (timeout, rate limit, overloaded) | Up to two retries, exponential backoff (0.5s, 1.0s) |
| Model output fails schema validation | Feed the validator's own message back to the model **once**; if it fails again, record a failed step and let the planner decide what to do |

A step that exhausts its policy is written into the trace as a failed step and
the planner is told. A planner that can see its own failures can route around
them; one that cannot will loop.

**The trace is an output, not a log.** Every step — including every failure —
becomes a `Step` with its tool, arguments, rationale, latency, token counts and
error kind. It is rendered on the result page, persisted with the run, and
asserted on in tests.

**Determinism under test.** The Claude client is a one-method protocol injected
into the loop. `AnthropicClient` wraps the SDK; `FakeClient` replays a scripted
list. The entire suite runs offline in about a second, which is why there are
tests for max-steps termination, schema repair, timeout classification and
guardrail rejection rather than hopeful prose about them.

### Where the model is constrained, and why

This is the part worth reading closely.

1. **Every model call is forced into a typed schema.** Each tool is a real
   Anthropic tool definition generated from the Pydantic model it returns, with
   `tool_choice` pinned to that tool. The model does not emit JSON in prose that
   we then hope to parse; it fills in a tool call, and Pydantic validates it at
   the boundary.

2. **The model may not author an `Evidence` object.** When scoring, it receives
   the retrieved passages with their ids and may only return *ids it was given*.
   The server rehydrates the snippet and score from what retrieval actually
   returned. A model that cannot construct an evidence object cannot construct a
   convincing fake one.

3. **The model may not report a number.** `hard_met` and `hard_total` are
   computed in `_assemble_report` from the verdicts. The scoring schema has no
   field for a total, so there is nowhere to put an unexplained one. A verdict of
   `met` or `partial` that cites nothing retrieval returned is rewritten to
   `gap`, whatever the model called it.

4. **Bullets are validated after the fact, in code.** `guardrail.enforce` runs
   after `draft_bullets` and before anything reaches the user. Every non-refused
   suggestion must cite at least one `doc_id`, and every id it cites must appear
   in the evidence retrieved *for that requirement* — not merely somewhere in
   the corpus, and not under a different requirement. Anything failing either
   check becomes `refused=True, refusal_reason="failed grounding validation"`,
   and the discarded draft is logged but never displayed.

   The prompt also asks the model to behave. Both layers exist deliberately: the
   prompt is how you get good behaviour most of the time, the validator is how
   you get a guarantee. A prompt cannot be tested, only sampled.
   `tests/test_guardrail.py::test_fabricated_citation_becomes_a_refusal` proves
   the validator catches a fabricated citation.

**Refusals are shown, not hidden.** They are the most informative thing on the
page: a refusal says the corpus contains no evidence for a requirement, which is
both the honest answer and the one that survives an interview.

## Design decisions and tradeoffs

Full list in [DECISIONS.md](DECISIONS.md). The ones that shaped the system:

**BM25 over a vector database.** The corpus is one resume and a few project
write-ups — a few dozen chunks. `rank_bm25` runs in-process, needs no service,
returns exact and explainable scores, and rebuilds at startup in milliseconds.
An embedding store would add infrastructure, a network hop and an opaque
similarity number to a corpus small enough to read end to end. The cost is
paraphrase, and it is a real cost — see Known limitations.

**Section-level chunks, not whole files.** A citation reading `resume#databases`
points at a paragraph a reviewer can check. One reading `resume` points at a
resume and proves nothing.

**The planner does not receive the corpus.** Where an argument is fixed for the
run (the job description) or is large derived state (the evidence map), the loop
supplies it from run state and the planner-facing schema takes no argument for
it. Round-tripping evidence through the planner would burn tokens and give the
model a chance to paraphrase it in transit — the exact failure the guardrail
exists to catch. The planner still chooses *which* tool, *which* requirement to
retrieve for, and *when* to stop.

**One provider, called directly.** No abstraction layer over LLM providers.
There is one provider; a second one is a refactor, not a design constraint, and
premature indirection here buys nothing but a layer to read through.

**A missing API key degrades `/health` rather than crashing the process.** A
container that boots and reports `anthropic_api_key: fail` is far easier to
diagnose than one that crash-loops before it can answer a probe.

**Metrics are in-process counters, not Prometheus.** Single process, no external
infrastructure. `/metrics` returns JSON. The latency window is bounded at 500
runs, which makes it answer "how is it behaving now" — the question you ask
during an incident — rather than "how has it behaved forever".

## Known limitations

These are real, and the project would be worse if it claimed otherwise.

- **BM25 fails on paraphrase.** Lexical matching is the central weakness. A
  requirement for "container orchestration" will not retrieve a resume section
  that says "Kubernetes", because they share no tokens. The system then reports
  a gap and refuses to draft a bullet — a *false* refusal, with no signal
  distinguishing it from a true one. This is the single highest-value thing to
  fix, and the fix is a hybrid retriever: BM25 for exact technical tokens, plus
  embeddings for paraphrase, merged by reciprocal rank fusion.

- **Long job descriptions degrade quietly.** The whole JD goes into
  `parse_requirements` in one call, and a truncated preview goes to the planner
  on every step. A very long posting inflates cost per step and can push
  requirement extraction toward the parts of the text the model weights most.
  There is no chunked-parse path and no explicit length guard.

- **Cost and latency scale with requirement count.** A run is roughly
  `2 + n_retrievals` model calls: one planner call per step plus one call each
  for parsing, scoring and drafting. Retrieval itself is free (no model), but
  each retrieval still costs a planner call to decide on. A twelve-requirement
  posting is comfortably a dozen-plus calls, and `MAX_STEPS=12` means a posting
  with many requirements can hit the ceiling before scoring — which is reported
  honestly as `terminated_reason: max_steps`, but is still a truncated answer.

- **The guardrail checks grounding, not truthfulness.** It guarantees a bullet
  cites a document that retrieval actually returned for that requirement. It
  cannot tell whether the bullet *fairly characterises* what that document says.
  A model that cites a real passage and overstates it will pass. Read the
  bullets.

- **Corpus quality is the ceiling.** The shipped documents are placeholders
  marked `TODO: replace`. Until they are replaced with real content, every
  interesting requirement is a gap. Garbage in, honest refusals out.

- **Abandoned timeout threads.** A call that exceeds `TOOL_TIMEOUT_S` is
  abandoned rather than cancelled — Python offers no way to interrupt an
  arbitrary blocking call. The worker is left to the SDK's own timeout. Under
  sustained upstream slowness this leaks threads for the length of that timeout.

- **Single process, single node.** SQLite, in-memory metrics, in-process index.
  Horizontal scaling would need all three replaced. This is a deliberate choice
  for a portfolio project, not an oversight — but it is not a design that
  survives a second replica.

- **No evaluation set.** There is no labelled corpus of job descriptions with
  known-correct verdicts, so prompt changes are validated by reading output, not
  by a score. That is the honest state of it.

## Observability

**Structured logs.** One JSON object per line, one line per event. The request
id is held in a `ContextVar`, set by middleware, and injected by the log
formatter — so "every line carries a `request_id`" is true by construction, not
by discipline. It survives the hop into the loop's worker threads because
`_with_timeout` submits through `copy_context()`. It is also echoed on the
response as `x-request-id`, so a user-reported problem maps to its log lines.

```json
{"ts":"2026-08-30T12:00:16Z","level":"info","logger":"jobhunt","request_id":"8b3ab3a225d8","event":"step_ok","step":2,"tool":"retrieve_evidence","latency_ms":143,"tokens":240,"summary":"3 passages, top resume#databases @ 6.271"}
```

**`GET /health`** reports each dependency separately and returns 503 unless all
are ok — SQLite round-trips a real query, the corpus index reports its document
count, and the API key is checked for presence:

```json
{"status":"ok","model":"claude-sonnet-4-5","checks":{
  "sqlite":{"status":"ok","detail":"ok","path":"/data/runs.db"},
  "corpus":{"status":"ok","detail":"ok","documents":3},
  "anthropic_api_key":{"status":"ok","detail":"present"}}}
```

**`GET /metrics`** returns run count by termination reason, per-tool call and
failure counts, p50/p95/max run latency over a bounded window, input/output
token totals, guardrail rejections, and error counts for every member of the
taxonomy.

**Error taxonomy.** Every failure maps to exactly one `ErrorKind`:
`upstream_timeout`, `upstream_rate_limit`, `schema_validation`,
`tool_execution`, `max_steps_exceeded`, `corpus_empty`. Steps carry the kind in
`Step.error`; metrics count by it. "What is breaking" is answerable without
grepping log text.

**Alert condition.** Page when **either** holds:

- `metrics.latency_ms.p95 > 30000` (p95 run latency above 30s), **or**
- `metrics.alerts.max_steps_rate_last_20 > 0.10` (more than 10% of the last 20
  runs terminated at `max_steps`).

The first catches upstream slowness and retry storms. The second catches the
failure mode that does not look like an error at all: the planner looping
without converging, which returns a plausible-looking page with a truncated
report. Both values are served directly by `/metrics` under `alerts`, alongside
their thresholds, so the alert rule is a comparison rather than a computation.

## Local setup

```bash
pip install -r requirements-dev.txt
export ANTHROPIC_API_KEY=sk-...          # optional: MODEL, MAX_STEPS, DB_PATH, LOG_LEVEL, TOOL_TIMEOUT_S
uvicorn app.main:app --reload            # http://127.0.0.1:8000
```

**Fill in the corpus first.** `app/corpus/documents/` ships three placeholder
markdown files — `resume.md` and two `project-*.md` — whose bodies are marked
`TODO: replace`. Replace them with your real resume and project write-ups,
keeping the front-matter `id` and the `## ` headings; each heading becomes one
separately citable chunk. Until you do, every requirement scores as a gap and
every bullet is refused, which is the system working correctly on an empty
corpus.

```bash
pytest                            # 81 offline tests, ~1.5s; the one live-API test skips without a key
ruff check app tests scripts
python scripts/smoke_live.py      # one real API run; needs ANTHROPIC_API_KEY
python scripts/render_sample.py   # regenerate docs/sample-report.html
docker build -t job-hunt-agent . && docker run -p 8000:8000 -e ANTHROPIC_API_KEY=sk-... job-hunt-agent
```

CI runs lint and the offline suite on every push, then builds the image and
asserts the container answers `/health` with per-dependency status. The one
live-API test skips itself when no key is present, so CI is deterministic and
free.
